# Contrato de evidencia y evaluación — 038

## Entrada v1

`python3 scripts/validate_038_evidence.py --input <evidence.json> --output <report.json>` recibe un único objeto JSON UTF-8. El esquema normativo es [validation-evidence.schema.json](validation-evidence.schema.json); [validation-evidence.example.json](validation-evidence.example.json) es una entrada estructuralmente válida pero sintética, que debe producir `blocked`, nunca `closed`. La interfaz es local al banco de validación y no cambia herramientas públicas de gomemory. El evaluador usa biblioteca estándar, no ejecuta texto capturado ni accede a la red.

La raíz contiene exactamente `schema_version=1`, `agent_profile`, `session`, `queries`, `calls`, `comparisons`, `surface_checks` y `regression_checks`. No se admiten campos adicionales en objetos tipados. `arguments` conserva el objeto JSON de argumentos originales de cada llamada; sus claves específicas dependen de la herramienta. La tabla precisa las relaciones que JSON Schema no expresa:

Los archivos intermedios no son entradas alternativas del evaluador. `query-manifest.json` contiene exactamente `{ "schema_version": 1, "queries": [...] }`; `observations.json` contiene `{ "agent_profile": {...}, "session": {...}, "calls": [...] }` con solo llamadas `observed`; `references.json` contiene `{ "calls": [...] }` con solo llamadas `reference`. T027 copia esos objetos sin editar sus campos a `evidence.json`, añade `comparisons` y checks, y comprueba que `session.manifest_sha256` sea el SHA-256 de los bytes originales de `query-manifest.json` y que `queries` sea igual al array decodificado del manifiesto. No se admiten consultas nuevas ni cambios de elegibilidad al consolidar. Las rutas/digests de cada `capture` enlazan las llamadas con las trazas locales; `session.mcp_sha256` enlaza ambos lados con el mismo binario.

| Campo | Tipo y regla |
|---|---|
| `agent_profile` | `agent`, `version`, `rewrite_status` (`supported`, `unsupported`, `unknown`) y `capability_evidence`, todos obligatorios. |
| `session` | `id`, `mode` (`tui`, `exec`, `synthetic`), `repository_revision`, ruta y SHA-256 del manifiesto, SHA-256 del binario MCP y `codec_id=codex-tui-visible-text-utf8-v1`. Solo `tui` puede cerrar. |
| `queries[]` | IDs únicos, prompt natural, elegibilidad con motivo, `comparison_key`, listas no vacías de hechos/referencias con IDs únicos por consulta y `manual_tool_coaching` booleano. Debe existir una comparación por consulta elegible. |
| `comparison_key` | `tool_family`, `source_scope`, `source_revision`, `query`, `filters` como lista ordenada de strings y `limit` entero positivo. El par compara estos seis campos por igualdad estructural exacta; `compression` queda fuera de la clave. |
| `calls[]` | IDs únicos globales, `query_id` existente, lado `observed` o `reference`, herramienta, ruta, compresión, argumentos originales, clave, `visible_text` y `capture`. Una referencia usa `compression=none`; una observación mantiene el valor realmente utilizado. |
| `capture` | `point`, `session_id`, ruta y SHA-256 del payload local protegido, `agent_version`, SHA-256 del binario MCP y mismo `codec_id` que la sesión. `point=codex_tui_model_input` solo si se comprobó la captura exacta; `unsupported` bloquea el par. La sesión de referencia puede tener otro ID, pero debe usar la misma versión de Codex, binario y codec. |
| `comparisons[]` | `query_id` único; `paired_calls` vincula cada recuperación equivalente observada con su referencia sin compresión; `additional_observed_call_ids` enumera recuperaciones extra que se cargan solo al lado observado. `review` identifica responsable, decisión de equivalencia y una referencia a llamada observada por cada hecho/referencia requerida. |

Para `capture_verified`, `evidence_ref` es la ruta local de `capture-certification.json` y el evaluador verifica su esquema, archivos y relaciones antes de `closed`; un booleano o una referencia arbitraria no bastan. `pytest_ci` demuestra la puerta nueva de CI. |

Cada ID de llamada aparece exactamente una vez en una comparación de su consulta: como miembro observado de `paired_calls`, referencia de ese par o llamada adicional observada. No puede aparecer en dos papeles ni en dos consultas. Las claves de cada par deben ser iguales entre sí y a la clave de la consulta; el evaluador rechaza referencias huérfanas, IDs duplicados y relaciones cruzadas. Todos los hechos y referencias requeridos deben tener IDs únicos y una entrada correspondiente en `review`, vinculada a una llamada observada de esa consulta. El evaluador no infiere suficiencia de un booleano sin esas referencias; la revisión humana aporta el juicio y responsable.

El parser rechaza UTF-8 inválido, claves JSON duplicadas en cualquier nivel, NaN/Infinity, enteros donde se exige booleano, strings vacíos donde se exige identificador y campos desconocidos. El evaluador verifica el SHA-256 del manifiesto y de cada payload a partir de las rutas locales declaradas, y comprueba que `agent_version` y `mcp_sha256` coincidan con el perfil y la sesión. `manifest_path` debe resolver dentro del repositorio; cada `trace_path`, dentro de `.memory/validation/038/`. Se rechazan escapes de esos directorios. Si no puede comprobar procedencia o reconstruir la respuesta visible, el estado es `blocked`. Ningún ejemplo sintético constituye evidencia de aceptación.

## Codec de respuesta visible v1

### Certificación del adaptador TUI antes de medir

`codex_tui_model_input` nombra un **requisito de observación**, no una API que se presuponga disponible. Para Codex 0.162.1, la ayuda local de `codex --help` y `codex debug prompt-input --help` no identifica una exportación de resultados de herramientas entregados al modelo en TUI. La [salida JSONL documentada de `codex exec --json`](https://developers.openai.com/blog/eval-skills) corresponde a la ejecución no interactiva y no prueba ese punto de la TUI. Por tanto, el estado inicial de este adaptador es `unsupported`; ninguna tarea puede marcar `capture_verified` a partir de esos comandos por sí solos.

T024 solo puede cambiarlo a certificado tras identificar una interfaz concreta de la versión instalada (API, evento y ruta de campo) **y un oráculo independiente que registre la entrada de la llamada al modelo**, con procedencia de implementación para ambos. No se acepta comparar dos exportaciones del mismo evento/campo. La prueba usa dos resultados MCP sintéticos conocidos dentro de TUI aislada: uno `observed` y otro `reference` con `compression=none`, IDs y marcadores distintos; entre ambos deben aparecer encabezado, metadatos, Unicode, CRLF y aviso. Cada extractor asocia sesión, llamada y orden sin ambigüedad y vuelca únicamente los bytes UTF-8 del resultado entregado. La traza del adaptador debe ser idéntica byte a byte a la porción correspondiente de la entrada del modelo en el oráculo de **esa misma llamada**. La mera coincidencia con el resultado MCP anterior a Codex, el render de pantalla, un resumen de eventos o una reconstrucción del payload no aprueba la certificación.

El artefacto local `.memory/validation/038/capture-certification.json` cumple [capture-certification.schema.json](capture-certification.schema.json). Contiene versión de Codex y hash del MCP, interfaz/evento/campo/referencia de implementación y ruta/hash de cada extractor, dos probes con `session_id`/`call_id`/`marker`/lado, rutas y SHA-256 del fixture y de ambas trazas, y revisión responsable con referencia a la inspección de procedencia. `surface_checks.capture_verified.evidence_ref` debe resolver a **ese archivo dentro de `.memory/validation/038/`**. Las rutas de fixture, extractor, traza y revisión también deben resolver dentro de ese directorio, sin symlinks que escapen. T020 exige al evaluador: esquema estricto; archivos existentes y hashes correctos de fixtures, extractores y trazas; lados `observed` y `reference`, IDs distintos y marcadores presentes; versión/MCP iguales a la entrada v1; tuplas `(interface,event,field_path)` distintas para adaptador y oráculo; trazas iguales byte a byte por probe; revisión `approved=true` y referencia de revisión existente. Si falta cualquier parte o la fuente de entrada del modelo no es verificable, la puerta falla con `blocked`, aunque `passed=true`. Una revisión humana de las referencias de implementación y del punto real de captura sigue siendo obligatoria: el JSON por sí solo no prueba que Codex expuso esa interfaz.

Si la versión no expone un registro de entrada del modelo con esa asociación o el contraste falla, registrar `point=unsupported` y `cause=measurement_unavailable` en `environment.json`; T029 publica `blocked` y T025–T028 quedan pendientes. No se fabrica un `capture-certification.json` aprobado ni un `evidence.json`, ni se afirma un exit del evaluador que no se ejecutó. Si existe una entrada v1 completa pero su certificado falta o falla, el evaluador sí devuelve exit 2. Un adaptador de una versión posterior exige nueva certificación. Esta decisión es determinista y evita presentar una ruta de éxito no comprobada como disponible.

`visible_text` es el texto Unicode completo que la captura comprobada en el punto `codex_tui_model_input` atribuye a **una entrega de resultado de herramienta**. Debe contener, en orden y literalmente, toda parte visible al modelo: encabezado, nombre/ruta, cuerpo, bloques de texto, metadatos, avisos, referencias de omisión y mensajes de error. La captura se obtiene después de decodificar el transporte y antes de que el modelo consuma el resultado. No se reconstruye desde un `CallToolResult` crudo ni desde un log de pantalla. Si la versión de Codex no expone ese punto de forma comprobable, se registra `point=unsupported` y la medición queda bloqueada.

`trace_path` designa un archivo **por llamada** que contiene únicamente los bytes UTF-8 exactos del payload visible en ese punto, sin prefijo, envoltura JSON ni salto de línea añadido por el capturador. El extractor abre el archivo en modo binario, verifica SHA-256, decodifica UTF-8 estrictamente y exige igualdad exacta con `visible_text`. Después comprueba que `len(raw_bytes) == len(visible_text.encode('utf-8'))`. La evidencia de que el capturador leyó el punto correcto se registra en `surface_checks.capture_verified.evidence_ref`; una afirmación sin preflight verificable no habilita `closed`.

El codec `codex-tui-visible-text-utf8-v1` toma la secuencia exacta de puntos de código de `visible_text` y calcula `len(visible_text.encode('utf-8'))`. No normaliza Unicode, espacios, saltos de línea ni finales CRLF; no añade separadores entre llamadas. Los delimitadores que el modelo realmente ve deben estar dentro del texto capturado. Se rechazan sustituciones por caracteres de reemplazo, surrogates sin pareja y bloques no textuales o estructurados cuya representación visible no pueda capturarse fielmente como texto. Campos de transporte no visibles quedan fuera solo porque no aparecen en el punto de captura, con la misma regla en ambos lados.

La referencia se obtiene **fuera de la sesión de aceptación** con compresión `none`, en una ejecución controlada que use el mismo punto de captura, codec, versión de Codex y binario MCP. Una respuesta MCP directa sin observar su representación en ese punto no es referencia válida. Si no se puede reproducir esa ruta, el par queda `blocked`. Se conservan metadatos variables y bytes entregados; si cambian hechos o impiden equivalencia, se bloquea el par, sin editar `visible_text`.

Para cada comparación, `reference_complete_bytes` es la suma de bytes de las llamadas de referencia emparejadas. `observed_complete_bytes` suma todas las llamadas observadas emparejadas y adicionales, incluida cualquier lectura de originales. Una respuesta cruda vista antes de comprimirse cuenta en ambas entregas. Los IDs exclusivos impiden doble atribución. `delta_bytes = reference_complete_bytes - observed_complete_bytes` y `saving_percent = 100 * delta_bytes / reference_complete_bytes`; la referencia debe ser positiva y el delta puede ser negativo. El informe registra cantidades, unidad `utf8_bytes`, codec, sumas y método. No equivale a tokens facturados ni usa `pack_savings` histórico.

## Estados

- `closed`, exit 0 del **evaluador de ahorro**: sesión TUI real; al menos tres consultas elegibles previamente fijadas usan la vía prevista sin coaching; claves y capturas comparables; hechos/referencias preservados; checks satisfechos y ahorro agregado positivo. El cierre de la feature exige además la revisión conductual negativa independiente descrita abajo; un `closed` del evaluador por sí solo no la sustituye.
- `pending`, exit 1: evidencia completa y comparable, pero falla conducta, conservación, consistencia o ahorro positivo; informar motivos por consulta.
- `blocked`, exit 2: falta TUI, captura exacta, referencia, digest comprobable o formato visible soportado. JSON inválido también termina con exit 2, sin informe exitoso.

El resultado separa incompatibilidad del agente, conflicto de instrucciones, ausencia de uso y fallo de recuperación. No diagnostica fallo del motor o hook sin evidencia específica. El manifiesto se fija antes de la sesión y no se sustituyen consultas fallidas ni se omiten recuperaciones caras. Un test simulado nunca produce `closed`.

## Observación conductual negativa independiente

FR-005 y SC-005 exigen una observación del agente, además de fixtures y pruebas de protocolo. Antes de la aceptación, `evidence/fallback-manifest.json` fija un prompt natural para obtener el cuerpo literal de una función Go conocida, dato que la recuperación comprimida estructural no proporciona por sí sola. Debe declarar el símbolo/archivo de referencia y el criterio de éxito: el agente usa una fuente alternativa que entregue el cuerpo, comunica que la vía estructural es insuficiente y no presenta el resultado como comprimido sin evidencia. El hash del manifiesto se registra antes de iniciar la TUI.

En la misma sesión real, **después** de las tres consultas elegibles, se envía este prompt sin nombrar herramientas ni instruir el fallback. `fallback-observation.json` conserva ID de sesión, hash del manifiesto, prompt, llamadas/rutas observadas, texto de respuesta final saneado y una revisión humana con responsable y tres decisiones explícitas: alternativa usada, motivo comunicado y ausencia de promesa de compresión. Si cualquiera falla, FR-005/SC-005 y el cierre global quedan `pending`. Este caso no pertenece a `queries`, `calls` ni `comparisons` del esquema de ahorro v1; sus bytes no entran en el numerador ni denominador de SC-003. Si no se puede observar la sesión, queda `blocked`, sin aprobar conducta a partir de instrucciones solamente.

## Privacidad y casos de prueba

Usar código y consultas públicos o sintéticos. Las trazas originales permanecen locales con permisos restrictivos; solo se versionan resumen saneado, hashes y referencias no sensibles. No copiar autenticación ni desactivar sandbox o aprobaciones para la prueba.

Casos del evaluador: ahorro válido, overhead o recuperaciones adicionales que lo anulan, Unicode/CRLF, deltas negativos o nulos, firma frente a cuerpo, pérdida de hechos, claves de comparación distintas, parámetros crudos incoherentes, coaching, sesión `exec`, métricas históricas, captura no textual, punto de captura ausente, JSON duplicado, IDs cruzados y bytes visibles incompletos. Solo el caso con todas las puertas puede cerrar.
