## 2026-08-17

- **Definir una capacidad de gomemory en el formato del primer agente que la implementa reproduce, en el mecanismo, la misma asimetría entre agentes que la feature venía a corregir.** La primera versión del plan de la feature 019 ancló el determinismo del modo plan directamente en `permissionDecision` de Claude Code, tratando al resto de agentes como degradación. El usuario lo corrigió: una capacidad se define SIEMPRE como contrato neutral (comando + momento + formato de decisión), y los formatos por agente son traducciones, nunca la definición. Consecuencia práctica: el motor de decisión (`domain.EvaluatePlanShape`) no sabe nada de dialectos; la traducción vive aparte (`hook_dialect.go`) y se implementa/testea DESPUÉS del motor pero ANTES del primer hook concreto — si el hook se escribe primero, su dialecto se filtra al motor y el siguiente agente hereda la forma del anterior. **Regla: cuando una capacidad tenga más de un consumidor posible (agentes, canales, formatos), diseñar primero el contrato neutral y las traducciones como piezas separadas, nunca implementar directo contra el primer consumidor real "y generalizar después" — el "después" no llega, y el diseño queda con la forma del primero.**
- **El determinismo se ancla donde el mecanismo YA está documentado y verificado, no donde "debería" estar por diseño ideal.** La entrada al modo plan (`PostToolUse(EnterPlanMode)`) parecía el lugar natural para el determinismo, pero es "mejor esfuerzo" porque no hay garantía documentada de que todo agente ofrezca ese punto. El borde de SALIDA (`PreToolUse(ExitPlanMode)`) sí tiene un mecanismo con contrato: se puede devolver una decisión con motivo. La verificación en vivo (montar una sonda real, no asumir el comportamiento a partir de la documentación truncada) confirmó esto antes de escribir una sola línea del mecanismo — la puerta de decisión de la Fase 1 del plan bloqueaba explícitamente avanzar sin ese dato.
- **El presupuesto real de un canal (10 000 caracteres para salidas de hook) puede ser menor que el documento que se quería inyectar sin que nadie lo hubiera notado.** El método de descomposición atómica por sí solo pesa ~4.2 KB; sumado al historial del proyecto (hasta 24 KB por defecto), el documento de planificación excede el canal por diseño. Sin un recorte propio con prioridad explícita (método completo siempre > historial recortado > puntero a recuperar el resto), el truncamiento lo haría el runtime del agente, cortando por el final — justo donde vive la autoverificación y el formato de salida del método. **Regla: antes de inyectar un documento compuesto por un canal con tope conocido, medir el tamaño real de cada pieza contra ese tope explícitamente — no asumir que "cabe" porque cada pieza por separado es razonable.**
- **Cuando una tarea de una feature ya diseñada colisiona con la aserción de un test protegido existente, hay que distinguir si es una regresión accidental o la consecuencia PREVISTA de un requisito nuevo antes de decidir qué hacer.** Un test de la feature 013 (`TestHookMarkerResetsPerSession`) asumía "el segundo prompt de la sesión no debe re-inyectar `additionalContext`" — cierto antes de la feature 019, pero el nuevo requisito (recordatorio de modo plan en CADA turno, FR-003) lo contradice a propósito. No era una regresión: era exactamente lo que la tarea pedía. Se corrigió la aserción para comprobar específicamente lo que el test protegía de verdad (que el BOOTSTRAP completo no se reinyecte), no la ausencia total de contexto. **Regla: ante un choque así, preguntar primero "¿esta tarea, tal como está redactada, exige este cambio de comportamiento?" — si la respuesta es sí, corregir la aserción con precisión quirúrgica; si es no, detenerse y replantear.**
- **Verificar en vivo, dentro de la propia sesión de trabajo, es posible y más confiable que asumir el comportamiento de un agente a partir de su documentación.** Usar directamente las herramientas `EnterPlanMode`/`ExitPlanMode` de la sesión en curso —con una sonda temporal registrada en hooks— permitió confirmar en minutos que `PreToolUse(ExitPlanMode)` sí trae `tool_input.plan` completo (2461 caracteres, coincidencia exacta), pese a que el esquema PÚBLICO de esa herramienta no declara ese parámetro. Un candado autoinducido (la sonda denegaba `ExitPlanMode` incondicionalmente mientras el modo plan solo permitía editar el archivo de plan) se resolvió notando que Bash sí sigue permitido en modo plan — sin necesidad de pedir ayuda externa.

## 2026-08-15

- **Una feature "implementada y con tests verdes" puede llevar meses sin funcionar en ningún proyecto real si el test nunca ejerció el camino real.** `resolveHotspotFiles` (feature 010, v1.22.0/v1.23.0) llamaba a `search_code` (grep/BM25 de texto libre del proveedor externo) pasándole el `qualified_name` completo como patrón, asumiendo que eso hacía un match exacto. Contra un repo real, ese texto largo con puntos nunca gana el ranking BM25 — el primer resultado siempre era ruido no relacionado. La suite de tests nunca lo atrapó porque solo probaba `parseSearchCodeFile` con un fixture ya filtrado a mano (comparación exacta de `qualified_name`, código correcto), nunca la llamada real al CLI contra un repo real. Resultado: dos capacidades ya anunciadas en el README/docs (anotación de impacto al guardar, sección "🔥 Memoria conectada a código activo" de `mem context`) llevaban ~7 versiones sin hacer nada. **Regla: cuando un test unitario mockea/fixturea la entrada de una llamada a un proceso externo, verificar al menos una vez contra el proceso real con datos reales — un fixture "razonable" puede no representar cómo responde el sistema real (BM25/ranking, en este caso).**
- **`search_graph` con `qn_pattern` (regex anclada) es el mecanismo correcto para resolver un símbolo por `qualified_name` exacto contra `codebase-memory-mcp`; `search_code` es grep/BM25 de texto libre, no un lookup exacto.** Confirmado en vivo con el CLI real de ambas tools sobre el mismo símbolo. Si se necesita "dame el archivo/definición exacta de X símbolo conocido", usar `search_graph`; `search_code` es para "encuentra dónde se menciona esto" en lenguaje natural.
- **Al reproducir un bug de un proceso externo por CLI a mano en bash, verificar que el JSON que se está enviando sea JSON válido antes de sacar conclusiones.** Un intento de reproducción con `\.` sin escapar dentro de una cadena JSON entre comillas dobles de bash produjo un `Invalid \escape` real (confirmado con `python3 -c "json.loads(...)"`) que casi se interpretó como "el fix no funciona bajo carga" — cuando en realidad el bug estaba en el comando de prueba, no en el código Go (que sí escapa correctamente vía `encoding/json`). **Regla: antes de diagnosticar un fix como "intermitente" o "no funciona", validar el propio comando de reproducción con un parser real, no asumir que la cadena bash está bien formada.**

## 2026-07-04

- **La entrada del 2026-06-21 sobre el plugin de OpenCode quedó obsoleta y es lo contrario de lo correcto.** Aquella decía que OpenCode "requiere un subdirectorio por plugin" (`plugins/gomemory/plugin.ts`). Es al revés: OpenCode auto-descubre plugins como **archivos sueltos** en `~/.config/opencode/plugins/` (`gomemory.ts`, sin subcarpeta) — el código actual (`opencode_setup.go`) instala así y activamente borra la instalación anidada legada (`os.RemoveAll(pluginsDir/gomemory)`) porque OpenCode nunca la cargaba. La documentación (INSTALLATION.md, docs/MANUAL.md, docs/architecture.md) seguía describiendo la ruta anidada meses después del fix real en el código — nadie la sincronizó cuando se revirtió el enfoque. **Regla: cuando una lección quede invalidada por un cambio posterior, no basta con corregir el código — hay que grep por la ruta/comando vieja en TODOS los `.md` del repo (no solo el README), porque cada doc suele repetir el mismo dato de forma independiente.**
- Relacionado: `mem setup opencode` (scope proyecto) escribe el MCP en el `opencode.json` del proyecto actual, no en `~/.config/opencode/opencode.json` — y OpenCode nunca "referencia" el plugin desde ningún JSON, lo auto-descubre por convención de carpeta. Confirmado empíricamente con `opencode debug config` (ver [[bugfix opencode global scope]] / release v1.11.0): ese mismo comando reveló que sí existe un `~/.config/opencode/opencode.json` de scope usuario que se mergea con el del proyecto, lo que permitió agregar `opencode` a `globalScopeAgents`.

## 2026-06-22

- `session-start.sh` resolvía el binario como `BIN="${GOMMY_BIN:-mem}"`. `GOMMY_BIN` nunca se exporta en ningún hook, así que siempre caía al literal `"mem"`, ausente del `PATH` → `command not found`. El mecanismo para hornear la ruta absoluta (`{{BIN_PATH}}` en `replacePlaceholders`) ya existía pero el template nunca lo usaba. Mismo bug en `plugin/opencode/plugin.ts` (`mem serve` literal). **Regla: cuando un template de plugin necesite invocar el propio binario, usar siempre `{{BIN_PATH}}`, nunca un nombre bare que dependa del `PATH`.**
- Los hooks de Claude Code se registraban como `PostStartup`/`PreShutdown` en `claude_code_setup.go` y `hooks/hooks.json` — **esos eventos no existen** en Claude Code (los reales son `SessionStart`/`SessionEnd`). Una instalación nueva nunca dispararía esos hooks (fallarían en silencio, sin error visible). **Regla: verificar contra la documentación real de eventos de hooks del agente, no asumir nombres "parecidos".**
- `//go:embed plugin` (sin el prefijo `all:`) excluye silenciosamente archivos/directorios que empiezan con `.` — por eso `.claude-plugin/plugin.json` y el `.mcp.json` del template nunca se copiaban a proyectos instalados, a pesar de estar documentados. **Regla: cualquier directorio embebido que incluya archivos `.algo` necesita `//go:embed all:dir`, no `//go:embed dir`.**
- `.mcp.json` es local y gitignorado — si el proyecto se clona/copia a otra máquina o usuario, queda con una ruta de binario stale (vimos un path de macOS de otro usuario en un checkout Linux). Reinstalar (`./mem setup claude-code`) lo regenera porque `InstallClaudeCode` sobreescribe la entrada `gomemory` sin condición.
- El flag `--target` de `mem setup` se pierde si se pasa el agente posicional ANTES de los flags (`mem setup claude-code --target X`) — el paquete `flag` de Go deja de parsear flags en el primer argumento no-flag. Hay que pasar `mem setup --target X --port N claude-code` (flags antes del posicional) para que efectivamente se respete.

## 2026-06-21

- `mem setup opencode` instalaba `plugin.ts` como archivo plano en `~/.config/opencode/plugins/` en vez de dentro de `~/.config/opencode/plugins/gomemory/plugin.ts` — OpenCode requiere un subdirectorio por plugin (`plugins/<name>/plugin.ts`). Fijado cambiando el target dir en `opencode_setup.go`. **⚠️ OBSOLETA, ver 2026-07-04**: esta conclusión resultó ser incorrecta y fue revertida — OpenCode sí auto-descubre archivos sueltos, el código actual vuelve a instalar `gomemory.ts` plano.
- El embed `//go:embed` no soporta `..` en la ruta del patrón. Solución: declarar el embed en `main.go` (raíz del módulo) y asignarlo a `setup.PluginFS` via `init()`.
- Los tests de Go deben estar en el mismo package que el código que prueban. `tests/unit/` con `package main` no compila — mover tests a `adapters/primary/mcp/server_test.go` e `adapters/primary/setup/setup_test.go`.
- `replacePlaceholders` en `setup.go` hacía `bytes.ReplaceAll` asignando a `string` en vez de `[]byte` — error de tipos al cambiar entre string y []byte sin conversión explícita.

## 2026-06-18

- `mem settings` was implemented (`cmd_settings.go`, registered in `main.go`'s dispatcher) but never added to `usage()`, README.md, or architecture.md — same recurring pattern as `setup-mcp` before it. **Rule: whenever a new `case` is added to the dispatcher switch in `main.go`, add it to `usage()` and the docs command tables in the same commit, not later.**
- MCP server configs generated by `setup-mcp`/`install` only ever wrote `args: ["mcp"]`, with no project root info. `mem mcp` resolves its project via `os.Getwd()` (`store.FindRoot()`), but the MCP client controls the subprocess's actual `cwd` when it spawns the server — never guaranteed to be the installed project. Root cause of "memories not saving after install even though the server shows as connected". **Fix: never rely on the spawning client's cwd for a server that must resolve a specific project — pass the project root explicitly as a CLI arg (`--root`) baked into the generated config.**
- A previous "global Claude config" write (`~/.claude/mcp/gomemory.json`) was dead code — Claude Code does not read per-server files from that path; its real global/user scope lives in `~/.claude.json`, and project scope (which actually works) is `.mcp.json`. **Rule: before writing integration code for an external tool's config format, verify the real schema/location (web search or official docs) instead of assuming a plausible-looking path.**
- Codex CLI's MCP config (`~/.codex/config.toml`) is a single global file shared across all projects with TOML tables `[mcp_servers.<name>]` — unlike the per-project JSON files used by other agents. **When adding a new agent integration, check whether its config is project-scoped or globally shared; globally shared configs need a unique key per project (e.g. `gomemory_<project>`) and must only be appended to, never fully rewritten, to avoid corrupting unrelated entries.**
