## 1. Objetivo y alcance

Se auditó el release que cierra HCD-013: política única de borrado
(`forget`, `purge`, `gc`, consolidación y TUI), garantía física en
`mem.db`/WAL, retirada de copias en `compression_originals`, migración v7,
`secure_delete` en el DSN, contrato de limpieza pendiente, envoltorios de
Socrática, `install.sh --uninstall`, plugin de OpenCode v1 y huella del
consenso ACR.

Fuera de alcance, declarado: validación de `mem import`, enlaces de
`mem export`, `Workspace.Run` de HCD, `target_type` de `review_start`,
`pruneSnapshots`, `opencode.jsonc`, CI y diversificación de modelos.

## 2. Metodología y límites

- **ADM:** un solo agente, dos pasadas: (A) correctitud funcional y contratos;
  (B) lente defensiva/seguridad (secretos, rutas, symlinks, escrituras
  atómicas, errores expuestos).
- **ACR:** **independencia degradada**. Los dos revisores previstos se
  lanzaron como subagentes separados y ambos fallaron antes de ejecutar con
  `Insufficient Balance` (`request_id: ea9f71ef-103f-4b1d-872e-622cba4ac209`
  y `ffefbb01-ceb5-492d-8fa4-0a1eba1dd343`). La corroboración es, por tanto,
  de un único modelo en dos pasadas; **no se emite `APPROVED`**.
- **Herramientas no disponibles en el host:** `staticcheck`,
  `govulncheck`, `shellcheck`, `gitleaks`, `semgrep`. No se ejecutó un
  escáner de secretos ni un análisis de composición de dependencias.
- **Cobertura no ejercida:** Windows (solo se revisó la guarda `GOOS`), host
  real de OpenCode (las pruebas del plugin usan fixtures) y una base de
  producción de gran tamaño.

### ADM-01 — La comprobación de copia viva ignora la forma `título: contenido`

**Dónde.** `adapters/secondary/persistence/maintenance.go`

- `retirarCopiasExactas` (128-160) anota **dos** hashes por memoria borrada: el
  contenido y `título + ": " + contenido`.
- `algunContenidoVivo` (162-170) recibe solo `memoriaBorrada` y comprueba
  únicamente `b.content`, no la forma que produjo el segundo hash.
- `contenidoVivo` (197-211), para textos de menos de
  `domain.MinContenidoIntegro` (32 runas), exige igualdad exacta.

**Por qué falla.** Si se borra la memoria `T` = «T» / contenido «abc» y existe
una memoria viva cuyo **contenido** es exactamente «T: abc», el hash del
original «T: abc» se anota por la forma con título, pero la comprobación busca
«abc» y no lo encuentra. El original se elimina aunque su texto siga vivo.

**Reproducción determinista.** Con un overlay temporal (el repositorio no se
modifica):

```bash
d=$(mktemp -d)
cat > "$d/repro_test.go" <<'EOF'
package persistence

import (
	"testing"

	"mem/application/ports"
	"mem/domain"
)

func TestReproCopiaVivaFormaCorta(t *testing.T) {
	db, _ := abrirBaseDeBorrado(t)
	insertarMemoria(t, db, domain.Decision, "T", "abc")
	insertarMemoria(t, db, domain.Learning, "Otra", "T: abc")
	almacen := NewOriginalStoreRepository(db, relojFijo{}, 1, 1)
	ref := guardarOriginal(t, almacen, "proj", "T: abc")
	if n, err := PurgeMemories(db, ports.PurgeFilter{Project: "proj", Type: "decision"}); err != nil || n != 1 {
		t.Fatalf("purge: %d %v", n, err)
	}
	if !originalExiste(t, db, ref) {
		t.Fatalf("la copia %q sigue viva en una memoria y se eliminó", "T: abc")
	}
}
EOF
printf '{"Replace":{"%s/adapters/secondary/persistence/repro_test.go":"%s/repro_test.go"}}' "$PWD" "$d" > "$d/overlay.json"
go test -overlay "$d/overlay.json" -run TestReproCopiaVivaFormaCorta -count=1 ./adapters/secondary/persistence/
```

Resultado observado:

```text
--- FAIL: TestReproCopiaVivaFormaCorta (0.02s)
    repro_test.go:23: la copia "T: abc" sigue viva en una memoria y se eliminó
```

**Hueco de prueba.** `TestCopiaViva_ConservaSoloLoQueSigueVivo`
(`borrado_memorias_test.go:527-557`) cubre «corta viva» con el contenido plano
(línea 538), pero no el caso en que la memoria viva contiene la **forma con
título**. `TestCopiaViva_HashCompartidoEntreBorradas` usa un contenido largo, que
se salva por la rama de contención. Por eso la suite actual pasa.

**Impacto.** Contradice C-14 y C-28 de HCD-013 y la promesa literal de
`CHANGELOG.md` y `docs/DATABASE.md` («si una memoria viva del proyecto aún
contiene ese texto, la copia se conserva»). La ref del pack queda rota:
`RetrieveOriginal` devuelve `ErrOriginalNotFound`. El texto **no** se pierde de
forma irreversible porque sigue en `memories.content` de la memoria viva, lo que
acota la severidad a media.

**Cierre propuesto.** Llevar la forma junto al candidato y comprobar esa forma:

```go
type candidataCopia struct {
	memoriaBorrada
	forma string // b.content o b.title+": "+b.content
}

anotar := func(b memoriaBorrada, texto string) {
	hash := hashOriginal(b.project, texto)
	porHash[hash] = append(porHash[hash], candidataCopia{b, texto})
	hashes = append(hashes, hash)
}
// ...
vivo, err := algunContenidoVivo(ctx, tx, porHash[hash])
```

```go
func algunContenidoVivo(ctx context.Context, tx *sql.Tx, candidatas []candidataCopia) (bool, error) {
	for _, c := range candidatas {
		vivo, err := contenidoVivo(ctx, tx, c.project, c.forma)
		if err != nil || vivo {
			return vivo, err
		}
	}
	return false, nil
}
```

Y añadir el caso que falta:

```go
{"corta viva con la forma", "Titulo", "corto", "Titulo: corto", "Titulo: corto", false},
```

Validación: `go test ./adapters/secondary/persistence -run 'CopiaViva|PurgaCopias' -count=1`.

### ADM-02 — Identidad por título en decisiones de plan aprobado

**Dónde.** `adapters/primary/cli/cmd_hook.go:942-957` (`planTitle` usa el primer
renglón) y `adapters/secondary/persistence/memory.go:407-422` (dedup por
`project + type + title` dentro de la ventana) y `88-99` (el «dedup» es un
`UPDATE` que reescribe `content` y `title`).

**Por qué falla.** Dos planes distintos que empiezan con el mismo renglón
(«Plan», «Objetivo», «Plan de implementación»…) comparten título
`Plan aprobado: …`; el segundo actualiza la fila del primero dentro de los 7
días y **el contenido del primer plan se pierde**.

**Reproducción determinista** (mismo mecanismo de overlay):

```go
func TestReproPlanMismoTitulo(t *testing.T) {
	db, _ := abrirBaseDeBorrado(t)
	a, _ := InsertMemory(db, &domain.Memory{Project: "proj", Type: domain.Decision, Title: "Plan aprobado: Plan", Content: "plan A"})
	b, _ := InsertMemory(db, &domain.Memory{Project: "proj", Type: domain.Decision, Title: "Plan aprobado: Plan", Content: "plan B"})
	if a != b { t.Fatalf("sin colisión: %d y %d", a, b) }
	var contenido string
	_ = db.QueryRow(`SELECT content FROM memories WHERE id = ?`, a).Scan(&contenido)
	t.Logf("el plan A se perdió: id=%d quedó con %q", a, contenido)
}
```

Salida:

```text
=== RUN   TestReproPlanMismoTitulo
    repro_test.go:31: el plan A se perdió: id=1 quedó con "plan B"
--- PASS: TestReproPlanMismoTitulo (0.01s)
```

**Alcance.** Preexistente y fuera del diff de v2.43.1, pero relevante porque el
cambio del plugin de este release reenvía planes ya guardados ante un fallo de
`turn-end` (ADM-03) y porque la mitigación de ese reenvío depende justamente de
este dedup por título.

**Impacto.** Pérdida silenciosa de una decisión aprobada. No hay error ni aviso.

**Cierre propuesto.** Dar identidad explícita al plan en vez de confiar en el
título:

```go
mem := domain.Memory{
	Project:  project,
	SessionID: sessionID,
	Type:     domain.Decision,
	Title:    planTitle(plan),
	Content:  plan,
	TopicKey: "plan:" + hashCorto(plan), // p. ej. hex(sha256(plan))[:16]
}
```

Así dos planes distintos coexisten y un reenvío exacto hace upsert. Añadir dos
pruebas: dos planes distintos con el mismo título conservan ambos contenidos, y
un reenvío exacto no crea fila nueva. Validación:
`go test ./adapters/primary/cli ./adapters/secondary/persistence -run 'Plan' -count=1`.

### ADM-03 — Reenvío de `plan-approved` tras fallar `turn-end`

**Dónde.** `infrastructure/plugin/opencode/gomemory.ts:163-178`. El marcador
`lastCheckpointedMessage` solo avanza **después** de que `turn-end` persiste;
`plan-approved` se ejecuta antes, dentro del mismo bucle. Si `plan-approved`
guarda y `turn-end` falla, el `catch` emite `channel-error` y el siguiente
`session.idle` reprocesa los mismos mensajes y reenvía el plan.

**Estado.** No es un defecto con la configuración por defecto: el dedup por
título de ADM-02 hace que el reenvío sea un `UPDATE` idempotente. Sí lo es si el
ajuste `DedupWindowDays` es negativo (dedup desactivado) o si la ventana de 7
días expiró. Reproducción del efecto con el dedup desactivado:

```go
SetDedupWindowDays(-1)
InsertMemory(db, &domain.Memory{Project: "proj", Type: domain.Decision, Title: "Plan aprobado: Plan", Content: "plan"})
InsertMemory(db, &domain.Memory{Project: "proj", Type: domain.Decision, Title: "Plan aprobado: Plan", Content: "plan"})
// count(*) WHERE title = 'Plan aprobado: Plan' == 2
```

**Hueco de prueba.** Las pruebas nuevas del plugin cubren el marcador y el
reintento de `turn-end`, pero no el caso «plan + `turn-end` falla + segundo
idle»: no hay ninguna aserción sobre cuántas veces se llama a `plan-approved`
ni sobre el número de decisiones resultantes.

**Impacto.** Duplicación de memorias de decisión ante un fallo transitorio de
persistencia, solo en configuraciones sin dedup. Severidad baja.

**Cierre propuesto.** Resolverlo en el origen con la identidad explícita de
ADM-02 (`topic_key` por hash del plan) y añadir una prueba del plugin:

```js
test('v2: a failed turn-end does not duplicate the approved plan', async () => {
  const f = await v2Fixture({ outputs: { fail: ['hook turn-end'] } });
  f.setMessages([v2AssistantPlan('msg_030', 'Plan de prueba')]);
  await f.emit('session.idle');
  await f.emit('session.idle');
  assert.equal(f.hookCalls('plan-approved').length, 2); // el reenvío ocurre
  // y en Go: un solo id de decisión tras ambos envíos
});
```

Validación: `node --test infrastructure/plugin/opencode/gomemory.test.mjs` y la
prueba Go de upsert por `topic_key`.

### ADM-04 — `--uninstall` presenta un fallo de borrado como «no encontrado»

**Dónde.** `scripts/install.sh:121-128`:

```sh
if is_own_binary "$dir/$BIN_NAME"; then
  rm -f "$dir/$BIN_NAME" && ok "Eliminado $dir/$BIN_NAME" && removed=1
else
  ...
fi
...
[ "$removed" -eq 0 ] && [ "$kept" -eq 0 ] && info "No se encontró el binario $BIN_NAME instalado."
```

Si `rm` falla (directorio sin permiso de escritura, fichero inmutable), la rama
`&&` no marca `removed` ni `kept`, y el script afirma que no encontró el binario
y sale con 0.

**Reproducción determinista:**

```bash
tmp=$(mktemp -d)
mkdir -p "$tmp/bin" "$tmp/home" "$tmp/sistema"
printf 'gomemory-protocol-v12' > "$tmp/bin/mem"
chmod 555 "$tmp/bin"
sed "s#/usr/local/bin#$tmp/sistema#g" scripts/install.sh > "$tmp/install.sh"
HOME="$tmp/home" GOMEMORY_BIN_DIR="$tmp/bin" bash "$tmp/install.sh" --uninstall
echo "exit=$?"; ls "$tmp/bin"; chmod 755 "$tmp/bin"
```

Salida observada:

```text
rm: .../bin/mem: Permission denied
› No se encontró el binario mem instalado.
exit=0
mem
```

**Impacto.** Mensaje falso y código de salida 0 ante un fallo real; un script de
desinstalación no puede distinguir «no había nada» de «no pude borrarlo».
Preexistente en su forma, pero la función se reescribió en este release y su
contrato (C-20) es precisamente distinguir ambos casos.

**Cierre propuesto.**

```sh
if is_own_binary "$dir/$BIN_NAME"; then
  if rm -f "$dir/$BIN_NAME"; then
    ok "Eliminado $dir/$BIN_NAME"; removed=1
  else
    warn "No se pudo eliminar $dir/$BIN_NAME"; fallo=1
  fi
fi
...
[ "$removed" -eq 0 ] && [ "$kept" -eq 0 ] && [ "$fallo" -eq 0 ] && info "No se encontró..."
[ "$fallo" -eq 0 ] || exit 1
```

Añadir al test un directorio sin permiso de escritura (o un fichero inmutable
donde el sistema lo permita) y comprobar salida distinta de 0.

### ADM-05 — `DeletedCount` de consolidación no refleja lo realmente borrado

**Dónde.** `application/usecases/consolidate_memories.go:56` calcula el total
antes de aplicar; `60-82` aplica por grupos y borra en lote, pero no ajusta
`report.DeletedCount` con el resultado de `DeleteMany`. La TUI lo muestra en
`adapters/primary/tui/tui.go:947`.

**Por qué importa.** Si `applyGroup` falla a mitad, los grupos restantes no se
funden, pero el mensaje sigue diciendo «N fila(s) fundida(s)». En la TUI el
mensaje lleva prefijo de error, así que no se presenta como éxito; la cifra, aun
así, es incorrecta. Preexistente.

**Cierre propuesto.** Asignar el resultado real:

```go
deleted, err := memRepo.DeleteMany(project, fundidas)
report.DeletedCount = int(deleted)
```

y, si se quiere conservar el conteo de lo fundido antes del fallo, calcularlo a
partir de `fundidas` en lugar del total de grupos. Validación:
`go test ./application/usecases -run Consolidate -count=1`.

## 8. Conclusión

El release implementa correctamente la parte más difícil de HCD-013: una sola
política de borrado, transaccional, con garantía física razonable y un contrato
de errores coherente entre CLI, MCP, TUI y consolidación. La suite y los
contratos pasan, y las afirmaciones del changelog se sostienen salvo una.

La excepción es real y reproducible: la comprobación de «copia viva» no prueba
la misma forma que usa para calcular el hash, de modo que `mem forget`,
`mem purge`, `mem gc` o un borrado de la TUI pueden retirar un original cuya
ref sigue apuntando a texto vivo. Es un defecto acotado (contenido <32 runas,
forma `título: contenido`) y sin pérdida irreversible de información, pero
rompe una garantía publicada y deja una ref rota.

No se emite `APPROVED`. El veredicto es **`INCOMPLETE`** por independencia no
satisfecha, con un defecto confirmado pendiente de corrección.
