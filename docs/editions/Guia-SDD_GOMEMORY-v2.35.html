SDD y harness

La especificación es el contrato. El harness es todo lo que rodea al modelo para que lo cumpla.

SDD (Spec-Driven Development) invierte el orden habitual: la especificación, el plan y las tareas se escriben antes que el código, y el agente implementa contra ese contrato, no contra su propia lectura del pedido. Así cada feature deja artefactos revisables (spec.md, plan.md, tasks.md), y el agente puede avanzar tarea por tarea en vez de entregar un único cambio enorme.

Un harness es el andamiaje alrededor del modelo: reglas, herramientas, memoria, verificación y control de versiones. Un modelo capaz dentro de un harness pobre olvida decisiones entre sesiones, relee el repositorio entero en cada tarea y da por terminado lo que nunca probó. Esta guía arma un harness de cuatro capas:

Agente CLI
Claude Code, OpenCode o Codex. Lee y edita archivos y ejecuta comandos. Es la única capa que actúa sobre el proyecto.
Contrato · Spec Kit
Constitución, spec, plan y tareas. Define qué se construye y en qué orden.
Memoria · gomemory
Decisiones, bugs, sesiones y reglas de trabajo. Recuerda por qué se hizo cada cosa.
Estructura · grafos
codebase-memory-mcp y CodeGraph. Responden dónde está el código y quién lo llama.

Prácticas tomadas de «Effective harnesses for long-running agents» (Anthropic): avanzar en incrementos pequeños; escribir el progreso fuera de la conversación (aquí, en tasks.md y en la memoria); probar cada incremento de punta a punta antes de seguir, y cerrar cada sesión con el proyecto en un estado limpio para la siguiente.

Codex y la compresión de salidas

Codex no acepta el mecanismo con el que gomemory comprime la salida de las herramientas externas, así que esa compresión no funciona en Codex (mem doctor la marca como «no soportado»). Para explorar código en Codex, usa search_code y get_symbol de gomemory, que comprimen en origen.

Grafos de código

Los grafos indexan la estructura del código: símbolos, llamadas y dependencias. Desde gomemory 2.28 se pueden usar dos proveedores externos a la vez.

Grafo Go propio

Incluido en gomemory, sin dependencias. Indexa símbolos Go.

  • index_project · graph_status
  • search_code · get_symbol
  • list_dependencies
codebase-memory-mcp

Grafo multilenguaje basado en tree-sitter. Detecta hotspots (el código que más cambia o más se llama), anota el impacto al guardar memorias y sincroniza los ADR.

  • search_graph · trace_path
  • query_graph (Cypher) · get_architecture
  • detect_changes · manage_adr
CodeGraph nuevo

Responde preguntas sobre el código en una sola llamada y calcula quién llama a qué, el radio de impacto de un cambio y los tests afectados.

  • MCP: codegraph_explore
  • CLI: callers, impact, affected
  • status · sync
instalar los dos proveedores externos
# codebase-memory-mcp (Linux / macOS; añade --ui para la interfaz web)
curl -fsSL https://raw.githubusercontent.com/DeusData/codebase-memory-mcp/main/install.sh | bash

# CodeGraph
curl -fsSL https://raw.githubusercontent.com/colbymchenry/codegraph/main/install.sh | sh
#   Windows: irm https://raw.githubusercontent.com/colbymchenry/codegraph/main/install.ps1 | iex
#   npm:     npm i -g @colbymchenry/codegraph
codegraph install      # conecta su servidor MCP a los agentes

Activarlos en el proyecto

.memory/settings.json
{
  "code_graph_providers": ["codebase-memory-mcp", "codegraph"]
}
bash · por proyecto
mem settings --code-graph-providers=codebase-memory-mcp,codegraph   # equivalente al JSON
codegraph init         # una vez por proyecto: crea el índice local (.codegraph/)
codegraph status       # nodos, relaciones y archivos pendientes
mem index              # grafo Go propio + reindexa cada proveedor en orden
mem index --skip-graph # solo el grafo propio
mem context            # muestra el estado de ambos proveedores
Cómo se reparten el trabajo

gomemory consulta los proveedores en el orden de code_graph_providers. Para la anotación de hotspots y la sincronización de ADR usa el proveedor que ofrece esa función, codebase-memory-mcp. CodeGraph aporta totales, codegraph_explore y codegraph affected. Si uno falla, mem index informa y sigue con el otro. Los refrescos de CodeGraph se serializan con un lock del sistema operativo.

Ajustes útiles

mem settings --code-graph=false apaga los proveedores externos · --code-impact-annotation=false quita la anotación de impacto al guardar · --adr-sync=true activa la sincronización bidireccional de ADR (mem adr-sync status).

Armar el harness, paso a paso

Sigue los ocho pasos en orden. Cada uno indica el resultado esperado; si no lo obtienes, resuélvelo antes de continuar.

  1. Instalar las herramientas base

    Deja disponibles en la terminal uv, specify-cli, el agente CLI, gomemory y los dos grafos de código. Los capítulos 2 a 6 detallan cada instalación.

    verificar
    specify version && mem --version && claude --version   # o opencode / codex
codebase-memory-mcp --version && codegraph --version

    los cinco comandos muestran su versión sin errores.

  2. Preparar el repositorio

    Spec Kit crea una rama por cada feature, así que el proyecto necesita un repositorio git.

    bash
    mkdir -p ~/proyectos/mi-api && cd ~/proyectos/mi-api
git init -b main

    git status muestra la rama main sin errores.

  3. Inicializar Spec Kit antes que gomemory

    Crea .specify/ y los comandos del agente. Va antes que gomemory porque mem install solo copia la extensión gomemory-context si .specify/ ya existe.

    bash
    specify init . --integration claude
specify integration install codex        # opcional: segundo agente
specify extension add git                # ramas y commits por fase

    existen .specify/ y .claude/skills/speckit-*, y specify extension list incluye git.

  4. Instalar gomemory en el proyecto

    Registra el servidor MCP y los hooks, guarda las reglas y la constitución en la memoria del proyecto y copia la extensión gomemory-context.

    bash
    mem install . --agents claude,codex --scope project
mem doctor

    el resumen de mem install marca ✓ en «Extensión Spec Kit», «Constitución» e «Integración Claude Code».

  5. Registrar la extensión gomemory-context paso manual

    Spec Kit solo ejecuta los hooks de las extensiones registradas en .specify/extensions.yml, y mem install copia la extensión pero no la registra. Sin este paso, /speckit-specify no carga el historial del proyecto.

    bash
    cp -R .specify/extensions/gomemory-context /tmp/gomemory-context
specify extension add --dev /tmp/gomemory-context --force
specify extension list

    specify extension list muestra «gomemory Project History Context» con Hooks: 3 y estado Enabled. El hook carga el historial siempre antes de specify, y de forma opcional antes de plan y clarify.

  6. Activar los grafos de código

    Con los grafos activos, el agente localiza el código por símbolos y llamadas en lugar de leer archivos completos.

    bash
    mem settings --code-graph-providers=codebase-memory-mcp,codegraph
codegraph init
mem index

    mem context incluye la sección «Grafo de código externo» con los dos proveedores.

  7. Fijar constitución y reglas

    La constitución define cómo se escribe el código; las reglas de trabajo, cómo se trabaja (cuándo planificar, cómo verificar un cambio). Las dos se guardan en la memoria, y este paso copia la constitución al archivo que lee Spec Kit. El capítulo 8 explica cómo reemplazarlas por las del equipo.

    bash
    mem docs import constitution ./constitucion-equipo.md   # opcional: la del equipo
mem constitution --sync      # escribe .specify/memory/constitution.md
mem rules                    # reglas de trabajo vigentes

    el contenido de .specify/memory/constitution.md coincide con la salida de mem constitution.

  8. Abrir la primera sesión y versionar el harness

    Confirma que el agente recibe la memoria al arrancar y guarda en git solo los archivos que pertenecen al proyecto.

    bash
    claude
# en la sesión: el hook carga get_context() → verifica que aparecen las reglas
# → /speckit-constitution   (revisa la constitución sincronizada)
git add .specify specs .claude/skills && git commit -m "chore: harness SDD"

    el agente menciona las reglas de trabajo sin que se las pidas y git status queda limpio. El capítulo 13 indica qué ignorar.

Si instalaste gomemory antes que Spec Kit: vuelve a ejecutar mem install . después de specify init y continúa con el paso 5. El comando es idempotente: solo reescribe los archivos que difieren.

Garantías

Lo que el equipo editó nunca se sobrescribe al actualizar. Un documento que nadie editó se actualiza solo con mem update. La copia de --sync sigue la misma regla: si alguien la editó, gomemory avisa y no la toca. Un import fallido no destruye el documento anterior y los secretos pegados por error se redactan.

Extensiones, workflows y presets

Además de plantillas, Spec Kit 0.15 incluye un catálogo de más de 180 extensiones, un sistema de hooks y un motor de workflows.

Extensiones

Añaden comandos y hooks (before_specify, before_plan…) registrados en .specify/extensions.yml.

Workflows

Encadenan comandos con puntos de aprobación manual entre fases. El workflow speckit viene instalado.

Presets

Sustituyen plantillas (spec, plan, tasks) con prioridad configurable. Útiles para normas sectoriales.

Bundles

Paquetes versionados de extensiones, presets y workflows que se instalan juntos.

bash · extensiones
specify extension search                 # catálogo completo
specify extension search git
specify extension add git                # ramas, commits por fase
specify extension add bug                # triaje de bugs: .specify/bugs/<slug>/
specify extension add assess             # evaluar una idea antes de especificarla
specify extension add github             # issues desde tasks.md
specify extension add --dev ./mi-extension   # desde un directorio local
specify extension list | info <id> | disable <id> | update | remove <id>
bash · workflows, presets y bundles
specify workflow list
specify workflow info speckit            # pasos y gates del ciclo completo
specify workflow run speckit             # specify → gate → plan → gate → tasks → implement
specify workflow status | resume

specify preset search && specify preset add <id>
specify preset resolve plan-template     # qué plantilla se usará al final

specify bundle search && specify bundle install <id>
Workflow speckit

Ejecuta specify, plan, tasks e implement, y se detiene dos veces para pedir tu aprobación: después de la spec y después del plan. Si rechazas, se cancela. Acepta scope = full, backend-only o frontend-only, y usa la integración del proyecto (auto).

Catálogo comunitario

Las extensiones de autores externos aparecen como «discovery only» y no se instalan directamente. Revisa el repositorio antes de usar --from <url>: una extensión ejecuta scripts dentro de tu proyecto.

Modo plan

Antes de planificar, get_plan_context() (o mem plan-context) entrega el método de descomposición atómica y el historial. mem hook plan-guard valida la forma del plan.

Context packs

Reúnen solo el contexto que necesita una tarea, dentro de un presupuesto de tokens. Incluyen los artefactos de Spec Kit del feature activo, salvo que uses --no-speckit.

Revisión adversarial

Dos revisores independientes analizan el mismo cambio, y un defecto solo cuenta si ambos lo confirman. gomemory valida y guarda cada paso: el agente propone las correcciones, pero no decide el veredicto.

bash · desde la terminal
mem search "auth jwt"                                    # ¿se decidió algo antes?
mem pack build --task "refresh tokens JWT" --max-tokens 4000
mem review --diff                                        # o --commit <sha> | --file <ruta>
mem review show <id>                                     # objetivo → revisores → consenso → fixes → veredicto
mem mass --top 10                                        # memorias más centrales (no «más importantes»)
mem session end -s "Objetivo… / Hallazgos… / Logrado… / Próximos pasos… / Archivos…"

Cierre de sesión. Antes de dar algo por terminado, el agente llama a end_session(summary) con cinco secciones: Objetivo, Hallazgos, Logrado, Próximos pasos y Archivos. La siguiente sesión arranca con ese resumen en get_context(). Las sesiones con más de 4 h de inactividad se cierran solas.

Opcional · Octopus AAR

Router que decide si una tarea se queda con el agente principal o se delega a un subagente, y con cuánto contexto. Viene apagado; mientras lo esté, no registra herramientas MCP ni guarda datos. Se activa en la TUI: Configuración → «Octopus AAR». Regla guía: delegar es una optimización, no el comportamiento por defecto.

El flujo es idéntico. Solo cambia la forma del comando: /speckit.specify … en OpenCode y $speckit-specify … en Codex.

Reglas de campo y tips

Lecciones de proyectos reales, donde el proceso dio una falsa sensación de avance mientras los bugs seguían vivos.

El proceso se ajusta a la tarea
Un bug, o una paridad con un sistema que ya corre, no necesita SDD. Reproduce primero contra el sistema en ejecución (logs, curl, navegador), corrige y verifica ahí mismo. Para triaje estructurado existe specify extension add bug.
«Verde en tests» no es «funciona»
Un test vale lo que vale su fixture. Si el mock no refleja la respuesta real del upstream, el test pasa aunque el caso real falle. Verifica contra el contenedor en ejecución (docker exec, curl, logs).
«No se ve el cambio»: revisa el despliegue
Revisa el artefacto servido, la URL y la caché antes de tocar código. docker compose up reutiliza la imagen vieja; usa docker compose up --build.
La constitución dice cómo, no impone rituales
Describe capas y estilo. No apliques un requisito de la spec que rompa el flujo real del usuario sin contrastarlo antes.

Tips

Tareas atómicasSi una tarea se siente grande, divídela. Muchas tareas pequeñas y verificables valen más que una enorme.
Converge al cerrarEjecuta /speckit-converge antes del commit final: detecta lo que la spec pedía y el código no tiene.
Explora por grafoPide al agente trace_path, codegraph_explore o search_code antes de que lea archivos completos.
Hallazgos con cierreCuando detectes un riesgo, repórtalo junto con la propuesta para cerrarlo y la forma de comprobar que quedó cerrado.
Conflictos de memoriaSi dos memorias se contradicen, no asumas que la más reciente es la correcta: relee el código y registra el veredicto con judge_memories.
SecretosEnvuelve en <private>…</private> lo que no deba persistirse. gomemory también redacta tokens conocidos.
PlaywrightCon /playwright-cli en modo --headed puedes revisar imágenes rotas, espaciados y secciones. Para probar chat y landing a la vez, abre dos navegadores --headed.
