Guía de presentación para desarrolladores

Cómo explicar gomemory a un equipo técnico

Guion base, ejemplos y comparativa de transportes (stdio, SSE, HTTP) y hooks para presentar a un equipo de desarrollo cómo funciona la memoria local de gomemory y el flujo de trabajo con HCD.

Agentes: Claude Code · Codex · agy · OpenCode · Formato: HTML interactivo e imprimible a PDF
Apertura sugerida

"¿Cuántas veces le han explicado a Claude Code o a Codex cómo está armada su API o por qué descartaron una librería, para que dos días después, en otra sesión, vuelva a proponer el mismo cambio? Cada sesión de un agente empieza desde cero, y repetir ese contexto cuesta tiempo y tokens. gomemory guarda las decisiones del proyecto en una base local y aplica las mismas reglas y comprobaciones en cada sesión."

Nota: Empieza con un ejemplo concreto de contexto que el equipo haya tenido que repetir entre sesiones.
1

Qué resuelve gomemory

Almacenamiento local, presupuesto de contexto, flujo HCD y revisión sin historial
1. SQLite local fuera del repositorio

La memoria se guarda en ~/.local/share/gomemory (o %LOCALAPPDATA%\gomemory en Windows), sin añadir archivos Markdown al historial de Git. Registra decisiones, correcciones, arquitectura y preferencias, indexadas con FTS5 y ranking BM25.

2. Presupuesto de contexto

La ventana del modelo es limitada. Al iniciar una sesión, gomemory envía solo el resumen y el recordatorio que caben en el tope (~3.000 a 4.200 caracteres), comprime las salidas grandes de las herramientas y guarda los originales para consultarlos con mem pack.

3. Flujo HCD y comprobaciones

Una tarea no se cierra solo porque el agente lo afirme. El motor ejecuta las comprobaciones declaradas en cada tarea, exige ver primero el fallo en correcciones de bugs (--expect-fail) y vincula la aprobación al hash de Git del documento.

4. Revisión sin contexto: Splash

Cuando el mismo agente que redactó un diseño lo revisa, suele pasar por alto lo que ya sabe de la conversación. El subagente splash arranca sin la memoria del proyecto ni herramientas MCP y contrasta el documento solo contra el código del repositorio.

5. Idioma en caliente (es / en)

Las plantillas, memorias iniciales, bloques de contexto y avisos de hooks se eligen en mem install --lang es|en o se cambian con mem lang [es|en] sin reiniciar el servidor MCP.

6. Supertool expand en los 4 agentes

Los interruptores de mem expand (status, on, off) y las reglas de pre-tool como graph-before-grep aplican en Claude Code, Codex, Antigravity CLI (agy) y OpenCode.

Cómo resumirlo

"Piensen en gomemory como la bitácora técnica del proyecto. Al abrir sesión, el agente lee las decisiones previas de la base local y, antes de cerrar una tarea, el motor ejecuta las pruebas que demuestran que el cambio funciona."

2

El papel de quien desarrolla: definir qué y qué no

Tú fijas el objetivo y los límites; el agente propone el cambio dentro de ese alcance
Reparto de trabajo: La persona define qué problema quiere resolver y qué partes del sistema no se deben tocar. El agente redacta y ejecuta los pasos dentro de esos límites.
Paso Lo que hace la persona Lo que hace gomemory
1. Objetivo Describe en lenguaje natural qué necesita cambiar y por qué. Abre la unidad HCD y crea el documento hcd/HCD-NNN-slug.md.
2. Alcance Indica qué entra en el cambio y qué queda fuera. Registra los límites en el documento de la unidad para acotar las tareas.
3. Aclaración Responde las preguntas abiertas de /hcd-clarify (una a la vez). Incorpora las respuestas en la definición antes de pasar a las tareas.
4. Aprobación Revisa la definición y la aprueba en la ceremonia completa. Guarda la cita de aprobación junto con el hash del documento; si la definición cambia después, pide aprobarla de nuevo.
Guion sugerido

"No hace falta redactar un documento largo antes de empezar. Dices qué endpoint quieres cambiar, cómo vas a comprobar que funciona y qué módulos no quieres tocar. Si algo queda ambiguo, el flujo pregunta lo necesario y, cuando apruebas la definición, pasa a las tareas."

3

Transporte MCP: stdio frente a HTTP y SSE

Por qué gomemory se comunica por entrada y salida estándar en lugar de abrir un puerto local

El protocolo MCP (Model Context Protocol) permite usar distintos transportes entre el agente y el servidor de herramientas:

Mecanismo Cómo funciona Ventajas Cuándo se usa
stdio
(Standard I/O)		 El agente lanza mem mcp como proceso hijo y envía mensajes JSON-RPC por stdin y stdout. No abre puertos de red, no depende del firewall local y termina cuando se cierra el agente. Modo usado por gomemory en Claude Code, agy, Codex y OpenCode.
HTTP El cliente envía peticiones POST a un puerto TCP y recibe la respuesta en cada llamada. Compatible con proxies, balanceadores y herramientas HTTP estándar. Servicios MCP remotos o compartidos entre varias máquinas.
SSE
(Server-Sent Events)		 Conexión HTTP abierta (text/event-stream) por la que el servidor envía eventos al cliente. Permite enviar mensajes del servidor al cliente sobre HTTP sin usar WebSockets. Servidores MCP en red que necesitan enviar notificaciones o respuestas progresivas.
Cómo explicarlo

"¿Por qué usamos stdio en lugar de levantar un servidor HTTP en localhost? Porque en una herramienta local no necesitamos abrir puertos, lidiar con choques de puertos entre proyectos ni dejar demonios corriendo cuando cierras el editor. El agente lanza mem mcp como subproceso, habla con él por tuberías del sistema operativo y, al cerrarse el agente, el proceso termina con él."

4

Eventos del agente y hooks de gomemory

Cómo se conectan las notificaciones de cada cliente con las reglas del proyecto

Cada agente tiene sus propios nombres de eventos y formatos JSON. gomemory traduce esas entradas a un formato común para aplicar las mismas reglas en los cuatro entornos.

El evento (del agente)

Es el aviso que emite el agente en un punto de su ciclo: al abrir la sesión (SessionStart), al recibir un prompt (UserPromptSubmit) o antes de ejecutar una herramienta (PreToolUse). Su nombre y su JSON dependen de cada cliente.

El hook (de gomemory)

Es el subcomando mem hook <subcomando> registrado en la configuración del agente. Lee el payload, lo convierte a una estructura común y evalúa qué hacer: añadir contexto, comprimir una salida o bloquear un comando peligroso.

Flujo en tiempo de ejecución
Agente (Claude / Codex / agy)  ──[ Evento: PreToolUse ]──>
  └─> gomemory (`mem hook expand`)
        ├─> hook_dialect.go: lee el JSON del agente
        ├─> domain/rules.go: comprueba reglas (ej. destructive-shell o graph-before-grep)
        └─> Código de salida ≠ 0 (bloqueado)  ──>  el agente cancela la herramienta
Analogía rápida

"El evento es el aviso del agente antes de hacer algo: 'voy a correr este comando en la shell'. El hook es el filtro de gomemory que lee ese comando, comprueba las reglas del proyecto y decide si lo deja pasar o lo detiene."

5

Glosario rápido

Términos habituales al explicar gomemory
Harness
El programa que ejecuta el modelo de lenguaje en tu máquina (Claude Code, Codex, Antigravity u OpenCode), muestra la conversación y corre las herramientas en el proyecto. En corto: el cliente donde trabajas con el modelo.
Meta-harness
Capa que conecta varios harnesses distintos con la misma base de memoria, las mismas reglas pre-tool y el mismo flujo de tareas. En corto: cambiar de agente sin perder el historial ni las reglas del proyecto.
Lifecycle hook
Comando que el agente ejecuta automáticamente antes o después de una acción (arrancar sesión, enviar un prompt, llamar una herramienta o cerrar un turno). Similar a un hook pre-commit de Git, pero para las acciones del agente.
MCP (Model Context Protocol)
Protocolo JSON-RPC con el que los agentes descubren e invocan herramientas externas como save_memory, search_memories o get_context. Similar a LSP para editores, pero orientado a herramientas y contexto para modelos.
FTS5 + BM25
Extensión de búsqueda de texto completo de SQLite combinada con la función de relevancia BM25 para buscar en las memorias locales sin servicios externos. Búsqueda por palabras clave ordenada por relevancia dentro del propio archivo SQLite.
Presupuesto de contexto
Tope de caracteres que gomemory aplica al contexto de arranque y a las respuestas de memoria para no ocupar la ventana del modelo con entradas secundarias. Enviar primero lo relevante para la tarea actual y dejar el resto disponible bajo demanda.
HCD (Harness Continual Dev)
Flujo de trabajo de gomemory para llevar un cambio desde su definición y aclaración hasta las tareas, la implementación con TDD y la verificación con evidencia. Dos carriles según el tamaño del cambio: vía rápida para ajustes acotados y ceremonia completa para cambios con diseño previo.
Splash
Subagente de solo lectura que se lanza sin la memoria del proyecto ni herramientas MCP para revisar una definición o un diseño solo contra los archivos del repositorio. Un segundo par de ojos que lee el documento sin conocer la conversación previa.
Context pack
Paquete comprimido de memorias, código o salidas de herramientas que el agente puede recuperar por sección o rango cuando necesita el detalle original. Guardar el detalle aparte y traer solo el fragmento necesario con pack_retrieve.
graph-before-grep
Regla de pre-tool de mem expand que redirige las búsquedas con rg, grep o find hacia codegraph_explore o las herramientas del grafo cuando el proyecto ya está indexado. Evita recorrer archivos texto por texto cuando existe un índice de símbolos y llamadores.
mem lang (es / en)
Comando para cambiar entre español e inglés el idioma del contexto, las plantillas y los avisos de hooks del proyecto. Actualiza .memory/settings.json y aplica el cambio en la siguiente llamada sin reiniciar mem mcp.
Cierre sugerido

"Los modelos cambian cada pocos meses, pero las decisiones y las reglas de un repositorio duran años. Con gomemory ese historial se queda en tu máquina, fuera de Git, y acompaña a cualquiera de los agentes que uses."

A1

Los tres grafos de código y la regla graph-before-grep

Qué resuelve cada grafo, cómo se actualiza y por qué el hook redirige las búsquedas por texto

En un proyecto con gomemory pueden convivir hasta tres índices de código: el grafo propio de gomemory para símbolos y paquetes Go sin dependencias externas, CodeGraph para obtener en una llamada el código fuente junto con sus llamadores e impacto en más de 30 lenguajes, y codebase-memory-mcp para consultas estructurales y recorridos de arquitectura.

Aspecto Grafo propio (gomemory) CodeGraph (codegraph) codebase-memory-mcp
Función principal Índice Go integrado en el binario, sin herramientas externas. Exploración de código en una sola llamada con codegraph_explore. Consultas estructurales, rutas entre funciones y análisis de acoplamiento.
Lenguajes Solo Go (.go) 30+ lenguajes (Go, TS, JS, Python, Rust, Java, C#, C/C++, PHP…) Multilenguaje (tree-sitter)
Tools MCP / CLI search_code, get_symbol, list_dependencies, graph_status codegraph_explore search_graph, trace_path, get_code_snippet, query_graph, get_architecture
Actualización Incremental al cerrar el turno sobre los archivos .go editados. Watcher en vivo (~1 s) con el servidor MCP activo o codegraph sync. Refresco en segundo plano (~60 s) o indexado con mem index.
Qué significa el aviso locked by hook: gomemory expand · regla graph-before-grep: Cuando el agente intenta ejecutar rg, grep o find sobre código y recibe ese bloqueo, el índice del grafo está activo. El hook (que corre en un presupuesto de 150 ms y nunca lanza reindexados) detiene la búsqueda por texto plano para que el agente consulte directamente codegraph_explore o las herramientas del grafo. Si hace falta desactivar las reglas temporalmente, basta con ejecutar mem expand off rules.
